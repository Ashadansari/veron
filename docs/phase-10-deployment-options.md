# Phase 10 deployment architecture and provider review

Reviewed September 25, 2026 against provider documentation and published pricing. This is a shortlist, not a purchase, account setup, or final owner selection. USD prices exclude taxes and workload-specific usage; recheck provider pricing and regional availability before contracting.

## Application requirements

- Run the complete Next.js App Router server under the Node.js runtime. Pin Node 24 LTS; Next.js 16 requires Node >=20.9 and Prisma 7 requires Node ^20.19, ^22.12, or >=24.0. The project now declares Node `>=24.0.0 <25` and `.nvmrc` `24`.
- Build with `npm ci`, then `npm run build`; run the generated app with `npm start`. Do not put database-backed routes on the Edge runtime. This app uses `postgres`/Drizzle, Prisma-generated code, Better Auth, Server Actions, and dynamic server routes.
- Use managed PostgreSQL with TLS, private networking, tested backups/PITR, enough connection capacity, and compute in the same region. Runtime `DATABASE_URL` must work with the `postgres` driver. If the provider offers a transaction pooler, verify transaction and advisory-lock behavior before using it. Use its direct connection string in the controlled Prisma migration job; never print either value.
- Prisma is the only migration authority. Drizzle is the runtime query layer over the same schema. Run `npm run db:migrate:deploy`; never run Drizzle Kit migrations or `npm run db:seed` in production.
- Better Auth requires `BETTER_AUTH_SECRET`, canonical `BETTER_AUTH_URL`, the shared auth tables, and the new `rate_limit` table. Its limiter stores counters in PostgreSQL, so set database capacity and pool limits for all app instances.
- Khalti remains optional. Keep the key absent and `KHALTI_ENVIRONMENT=sandbox` until the merchant, externally reachable return URL, sandbox E2E, callback verification, and production approval gates are met. COD is independent and remains controlled by store settings.
- Product records store image URLs and metadata. Admins may use HTTPS URLs or a local/staging-only device upload stored beneath `public/uploads/products/`; this filesystem path is disabled in production, is not an object-storage/CDN integration, and must not be used on ephemeral or multi-instance production hosts. The storefront demo and sample catalog use Unsplash URLs; production product photography requires store-owned/licensed assets and durable image hosting. The current Next image allowlist only includes `images.unsplash.com`, so a chosen optimized-image host must be added deliberately and tested. Do not store production uploads on an app instance's ephemeral filesystem.
- `GET /api/health` checks PostgreSQL and returns only `ok` (200) or `unavailable` (503). Configure the selected platform to use this path for readiness; also set an independent uptime monitor because some platform health checks run only during deploy.

## Provider comparison

| Option | Fit for this app and Nepal | Database, operations, and limits | Cost shape (USD, before tax) |
|---|---|---|---|
| **Render** | Full Next.js Node web service and managed PostgreSQL are both supported; Singapore is available for both app and database. This is a practical first staging candidate for a conventional long-running Node app. | Native private networking, HTTP health checks that can check readiness and restart unhealthy instances, managed Postgres, deploy history, and custom domains/TLS. Put service and database in Singapore; verify actual Kathmandu latency. Paid service/database compute and storage are separate. Render does not support changing an existing service/database region in place. | Hobby workspace has no base fee; Pro workspace is $25/month, then service/database compute and storage. Published database storage is $0.30/GB; pricing lists a 3-day PITR window. Do not use free instances for production. |
| **Railway** | Next.js + PostgreSQL can live in one project; Singapore is an available region and private service references simplify connecting the app and database. Good operator simplicity and usage visibility. | Supports Next.js, PostgreSQL, service variables, deploy health checks, domains, and migrations as a pre-deploy command. Its docs note health checks validate new deployments, not continuing service health, so add external uptime monitoring. Configure backups/PITR and offsite logical dumps explicitly. | Hobby is $5/month and Pro $20/month, each applied as included resource usage; usage above the credit is billed by CPU, RAM, volume, and egress. |
| **Vercel + managed PostgreSQL** | Strongest Next.js-specific build/CDN experience. Vercel lists Mumbai (`bom1`) as a region, which is geographically attractive for Nepal. Pair app compute and the external Postgres provider in the closest common region. | PostgreSQL is supplied through Marketplace integrations (Vercel Postgres is no longer offered for new projects). Serverless Node functions mean connection pooling and migration use of a direct URL need explicit validation. Plan logs/alerts and backups across the platform and database provider. | Pro starts at $20/month with $20 usage credit; compute/traffic usage can add costs. Database pricing is separate and depends on the selected provider/plan. Hobby is documented for personal/non-commercial use, so not appropriate for this store. |
| **Fly.io + Managed Postgres** | Flexible regional Node/Docker deployment and separately managed PostgreSQL; suitable if the owner wants more control over machine sizing and networking. Confirm the same suitable APAC region is available to the chosen managed database plan before selecting it. | More configuration/operations responsibility than the PaaS choices above. Prefer Managed Postgres; Fly documents unmanaged Fly Postgres as unsupported. Size app and database, configure health checks, backup policy, alerts, and release procedure explicitly. | Usage-based machine, volume, and egress charges; Managed Postgres is priced by plan plus storage. The provider's published October 1, 2026 update lists Managed Postgres starting at $38/month plus $0.28/GB storage, effective after the review date. |

### Recommendation for owner review

Evaluate **Render first in a private staging environment**, paired with Render Postgres in Singapore. It most directly matches the current single Node server + managed PostgreSQL architecture and has deploy health checks and integrated database operations. Treat it as a candidate only: compare an actual monthly estimate, test Kathmandu latency, verify the required backup/PITR and access-control plan, and compare Railway and Vercel/Neon before the owner selects a provider. If Mumbai-region compute/database pairing and a global CDN matter more than a conventional always-on Node service, evaluate Vercel + a Mumbai-region Postgres provider as a separate candidate and test its pooler with both Prisma and Drizzle.
